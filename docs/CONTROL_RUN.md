**Фактический контроль 8 ноября завершён:** 10/10 полных оценок Gemini/v7.
Xerosharc отклонил первый вызов по балансу; применён ручной резерв и один
отдельный технический запуск failed-чата. [Отчёт и hashes](PROD_SUBMISSION_20261108.md).
Ниже сохранён исходный порядок запуска; не запускать его повторно для уже сданных чатов.

Основание — [отдельное решение по чатам](CONTROL_CHAT_PROFILE.md). Основной профиль
`boundary-xerosharc-v7-1` / `1`; резерв `boundary-gemini-v7-1` / `1`. Default
приложения остаётся v4, опубликованный DEV — исторический Gemini/v2. Голосования,
reviewer и автоматической смены провайдера нет. Общие правила формата и публикации
описаны в [SUBMISSION](SUBMISSION.md).

Ночная проверка 8 ноября: полный запрос Xerosharc отклонён из-за квоты
(`pre_consume_token_quota_failed`), хотя короткий запрос проходит. Перед контролем
проверить/пополнить квоту; `configured` и успешный короткий вызов недостаточны.
Не тратить контрольный час на повтор одинаковых отказов. Если основной запуск
ещё не начат и квота не восстановлена, оператор может явно выбрать весь запуск
Gemini: обычные evaluate/export/validate с `config-backup.json` и отдельным
`prod-backup.run.json`. Если основной запуск уже начат, применять описанное ниже
восстановление двух журналов. Успешные/partial Xerosharc не заменять.

Заморозка кода — **10:00 UTC+5**, организаторская сдача — 12:00.
Основной [сценарий защиты](DEFENSE_5_MIN.md) занимает не больше пяти минут.

## Подготовка до получения PROD

Профили из [examples/control-config](../examples/control-config/README.md) должны
быть установлены, оба ключа настроены локально. Для текущей рабочей установки API
доступен на `http://127.0.0.1:8001`, БД — `data/private/quality-v3/cqa.sqlite3`.
Сервер работает в production. Не использовать старый сервер на 8000 или тестовый
оценщик. При другой установке изменить API и БД согласованно.

PowerShell, корень проекта:

```powershell
$controlPython = '.venv/Scripts/python.exe'
$controlApi = 'http://127.0.0.1:8001'
$controlDir = 'data/private/control-20261108'
$controlDb = 'data/private/quality-v3/cqa.sqlite3'
& $controlPython -m cqa_submission init --api $controlApi --team-name Vtiposhniki --branch main --profile-id boundary-xerosharc-v7-1 --profile-version 1 --config "$controlDir/config-primary.json"
```

В текущей установке оба config уже подготовлены. При новой установке **один раз**
сохранить копию primary как `config-backup.json`, изменив только `profile_id` на
`boundary-gemini-v7-1`. `checklist_version_id`, команда, branch и версия профиля
остаются теми же. Не выполнять отдельный `init` для backup: он создаст другой
чек-лист. Не менять config/receipt начатого запуска. Дополнять `redactions` можно
без повторной AI-оценки; восстановление применяет объединение списков двух config.

На 8 ноября конфигурации проверены через API: оба профиля configured, default v4
по-прежнему preferred. Проверка конфигурации не является проверкой текущей квоты.
Эта подготовка выполнена до получения PROD; фактический результат указан выше.

## Основной путь

Сохранить **реально выданный** ответ организаторов как `prod.source.json` в
`$controlDir`. Не угадывать URL контроля и не использовать учебные данные.
Импорт проверяет ровно десять уникальных чатов и сохраняет исходные IDs/реплики.

```powershell
& $controlPython -m cqa_submission import --api $controlApi --source "$controlDir/prod.source.json" --dataset prod --manifest "$controlDir/prod.manifest.json"
$controlArgs = @('--manifest', "$controlDir/prod.manifest.json", '--config', "$controlDir/config-primary.json", '--run', "$controlDir/prod-primary.run.json")
& $controlPython -m cqa_submission evaluate @controlArgs --api $controlApi --interval-seconds 6 --timeout-seconds 900
```

На первом техническом отказе CLI останавливает дальнейшую отправку. Если требуется
продолжить с тем же доступным Xerosharc, повторить **тот же receipt** с
`--continue-on-failure --max-consecutive-failures 2`; уже принятые задания не
пересоздаются. Сбой/timeout CLI не означает отмену серверного задания. Не удалять
receipt и не создавать новые ключи ради повтора.

Если резерв не использовался:

```powershell
& $controlPython -m cqa_submission export @controlArgs --database $controlDb --output "$controlDir/prod.candidate.json"
& $controlPython -m cqa_submission validate @controlArgs --database $controlDb --file "$controlDir/prod.candidate.json"
```

## Явное переключение на Gemini

Основание — транспортный/квотный отказ или исчерпание исправлений формата,
оставившее job failed. Смысловое несогласие, низкий балл и `succeeded + partial`
**не являются** основанием для переключения. Первый доступный полный ответ не
выбирается из нескольких по удобству результата.

1. Остановить основной CLI (Ctrl+C), сохранить его receipt. Дождаться терминальных
   состояний уже отправленных jobs в интерфейсе. Не прерывать сохранение ответа.
   Только один оператор запуска управляет этими receipt; основной CLI после
   переключения больше не возобновлять параллельно с резервом.
2. Выполнить `plan` ниже. При queued/running/retry_wait он откажет: нужно дождаться
   завершения/серверного deadline, затем повторить план. План не вызывает AI.
3. Проверить eligible IDs: только `failed`, `cancelled`, `not_started`. Успешные
   complete и partial защищены. Если список пуст, резерв не запускать.
4. Явно выполнить `evaluate` для резерва. Тот же отдельный backup receipt позволяет
   возобновление; новые задания создаются только для перечисленных IDs. После
   двух новых последовательных отказов резерв прекращает отправку. Бесконечной
   цепочки провайдеров и нового смыслового голосования нет.

```powershell
$recoveryArgs = $controlArgs + @('--recovery-config', "$controlDir/config-backup.json", '--recovery-run', "$controlDir/prod-backup.run.json", '--database', $controlDb)
& $controlPython -m cqa_submission.recovery plan @recoveryArgs
& $controlPython -m cqa_submission.recovery evaluate @recoveryArgs --api $controlApi --continue-on-failure --max-consecutive-failures 2 --interval-seconds 6 --timeout-seconds 900
& $controlPython -m cqa_submission.recovery export @recoveryArgs --output "$controlDir/prod.candidate.json"
& $controlPython -m cqa_submission.recovery validate @recoveryArgs --file "$controlDir/prod.candidate.json"
```

Два полных receipt закрепляют один manifest и один официальный чек-лист, но разные
профили. Адаптер читает обе истории из SQLite, оставляет успехи/partial основного
запуска, берёт резерв только для технически недоступной части. При попытке заменить
успешную оценку или при расхождении закреплённых данных выгрузка блокируется.
Ошибка резерва остаётся error; partial не превращается в N/A. Оба исходных запуска
сохраняются, JSON не склеивается вручную.

`model.name` собирается из `CallRecord.actual` реально сделанных вызовов обеих
историй, включая подтверждённые вызовы неуспешной основной попытки. Обычно при
смешанном запуске это `gemini-3.5-flash-lite; xeros_core`. Если Xerosharc не сообщил
actual ни в одном вызове, его имя не выдумывается по конфигурации. Неиспользованный
резерв в модель не попадает. Только облачные вызовы означают `external_api`, не hybrid.

Идемпотентность защищает от повторного создания принятых jobs при повторе команды;
строго однократный внешний запрос при сетевом сбое не обещается. Встроенные
транспортные/форматные повторы остаются в лимитах профиля и в журнале расходов.

## Просмотр и сдача

Планировать около 15 минут на основной путь, до 15 на резерв и сохранить время
на просмотр всех 10 результатов и публикацию. Состоявшаяся репетиция заняла
8 мин 2 с целиком; это не гарантия будущей сети/квоты. Проверять оставшееся время
контрольного часа до переключения. При невозможности дождаться терминального
состояния `--allow-unfinished` в экспорте явно оформляет незавершённую часть как
error. Активный основной job всё равно блокирует переключение: в такой ситуации
доступен обычный однопрофильный экспорт, а не параллельный вызов Gemini.

Просмотреть все объяснения успешных оценок (80 при десяти полных оценках),
а для partial — внутреннюю карточку:

- C2: был ли необходим неизвестный факт до ответа; инструкция и C3 не подменяют discovery.
- C3/critical: общая информация, раскрытие конкретных данных и защищённое действие;
  порядок проверки; безопасная остановка при отказе клиента.
- C7: основной ответ, завершающий следующий шаг/резюме, прощание и возможность
  завершить диалог; не требовать отсутствующих в рубрике сроков/ритуальных фраз.
- C4 partial: назвать конкретный неизвестный факт; отсутствие KB само по себе
  не доказывает неопределимость. Не подставлять значение ради полного JSON.

Ручное наблюдение не переписывает automatic в официальном файле. В продукте
обращение/решение человека хранится отдельно. Удалить личные детали через
`redactions`, пересоздать кандидат и проверить его новый hash. На выходе ровно
исходные десять ID, схема/арифметика/evidence и происхождение проверены.

После просмотра присвоить `$reviewedControlSha` **фактический SHA-256 проверенного
кандидата**, напечатанный CLI. При использовании резерва:

```powershell
& $controlPython -m cqa_submission.recovery export @recoveryArgs --output results/prod/results.json --reviewed-sha256 $reviewedControlSha
& $controlPython -m cqa_submission.recovery validate @recoveryArgs --file results/prod/results.json
```

Без резерва использовать обычные `cqa_submission export/validate @controlArgs
--database $controlDb` с теми же `--output/--file` и проверенным hash. Не путать
резервный путь с обычным: обычный валидатор проверяет только один профиль.
Затем выполнить commit/push и удалённую проверку обоих официальных файлов из
[SUBMISSION](SUBMISSION.md#публикация-и-удалённая-проверка). Старый DEV не пересоздавать.
Успешный локальный экспорт без push не является законченной сдачей.

## Короткий сценарий защиты: около трёх минут

1. **Диалоги и доказательства.** «Система оценивает чаты и расшифровки звонков по
   изменяемому чек-листу. Откроем оценку и реплики, на которых она основана.
   N/A отличается от неизвестного ответа; critical показан отдельно от балла».
2. **Версии и человек.** Показать редактор, сохранённую пару оценок и сравнение,
   затем историю апелляции. «Новая версия не меняет старый запуск; решение человека
   сохраняется отдельно от исходного AI. Баллы рассчитывает доменный код».
3. **Профиль контроля.** «Для десяти контрольных чатов выбираем Xerosharc v7:
   99/123 против 90/123 у v4 в направленном аудите разработки, 59/60 полных чатов.
   Это не независимая точность. На звонках было ухудшение, поэтому общий default
   оставлен v4. Опубликованный DEV получен раньше на Gemini/v2».
4. **Устойчивость и честные ограничения.** Показать сводку сохранённого запуска:
   фактическую модель, calls, токены и неизвестную стоимость. «Шлюз сообщил
   xeros_core; внутреннюю модель подтвердить не можем. Остались границы discovery
   и closure, поэтому проверяем все десять результатов. При техническом отказе
   вручную запускаем Gemini только для оставшейся части, сохраняя успехи и оба
   журнала. Голосования нет».
5. **Сдача.** Показать реально опубликованный DEV и валидатор. PROD показывать
   только после получения и публикации настоящих данных. Репетицию на выдуманных
   чатах обозначать как репетицию, а дизайн-концепты — как концепты.

Во время короткой защиты не запускать полный DEV. Использовать сохранённые
примеры; дополнительный живой вызов — только если он нужен самой демонстрации.
