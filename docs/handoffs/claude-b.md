## Поиск диалогов по флагу (контракт 1.1.0)

Реализован [FLAG_FILTER_CONTRACT.md](../FLAG_FILTER_CONTRACT.md) в `conversations.py`.
Shared DTO и generated-файлы не менялись, OpenAPI сервера совпадает с контрактом. Миграция
не понадобилась. Временный guard501 и его тесты удалены.

- **Выбор результата.** Текущая `latest_revision` → `MAX(jobs.seq)` этой ревизии и точной
  `checklist_version_id` → только `jobs.evaluation_id`. Сначала выбирается job, потом
  читается флаг, поэтому историческая оценка не может удовлетворить фильтр.
- **Значение флага.** Единственный источник — `automatic_score_json.flags` или
  `effective_score_json.flags`, сохранённые из domain. Читается только при `succeeded`
  job и оценке `complete`/`partial`, иначе `FlagResult` с `null`.
- **Пагинация.** `COUNT` и страница используют один SQL-подзапрос с одним `WHERE`, в одной
  read transaction. Фильтр применяется до `COUNT`/`LIMIT`/`OFFSET`, порядок
  `conversations.seq DESC`, `LEFT JOIN` не теряет разговор без job.
- **Ошибки.** Неизвестная версия 404, не флаг выбранной версии 422 с
  `details[0].field=flag_criterion_id`. Комбинации параметров проверяет shared
  `conversation_flag_query`. Значение параметра в сообщение не попадает.
- **`evaluation_status`.** Теперь `failed`/`cancelled` дают `failed` всегда, в том числе если
  у job осталась оценка. Для `succeeded` статус берётся из artifact, независимо от scope.

### На что обратить внимание C

- Для списка с выбранным флагом строка есть всегда: pending, failed и unevaluated приходят
  с `status=unknown` и `detected=null`. `flag_summary=null` значит только «флаг не выбран».
- У `failed` может быть `latest_evaluation_id` (failed-артефакт) или не быть (сбой job).
  У pending и unevaluated его нет.
- Новый запуск, в том числе `reuse_if_compatible`, создаёт новую оценку без старых решений.
  Значит, после него effective снова равен автоматическому результату. Это следует из правила
  контракта и закреплено тестом; прежнее решение остаётся в старой оценке.
- Браузерная часть U01–U04 — зона C, здесь не проверялась.

**Deadline, пункт 1.** Изменение shared-интерфейса не понадобилось: A и так ограничивает
каждый вызов остатком времени и возвращает initial с `review_unfinished`. Запас не даёт
новых вызовов: после deadline `call_started` отклоняется. Он нужен только для того, чтобы
A успел записать завершение вызова и вернуть результат. Оценщик, который не уложился в
запас, отменяется, и задание получает `failed` с кодом `timeout`. Отмена, потеря lease и
сбой записи событий по-прежнему завершают попытку без успеха: это проверено на настоящем
`Evaluator` A во время зависшего reviewer.

Предложение интегратору: записать это правило в `docs/CONTRACTS.md`, файл не мой.

**Попытки, пункт 3.** Каждая начатая попытка считается, чем бы она ни закончилась: сбоем,
истёкшим lease или остановкой. Значит, три остановки подряд при `max_attempts=3` переводят
задание в `failed` с кодом `cancelled`. Ручной retry добавляет ровно одну попытку, бюджет и
deadline не сбрасываются. Поле `retryable` в ошибке теперь отражает, будет ли новая попытка.

**Фрагменты, пункт 5.** Сохранённый артефакт не меняется. Фрагмент вычисляется при каждом
чтении, поэтому переживает перезапуск. Текст источника, на который ссылалось уже заменённое
решение, остаётся доступен для истории решений. В экспорт текст не попадает, только ID.

## Как вызывается домен

Сервер обращается к `cqa_domain` и `cqa_ai` только через `ports.py`, формулы и
канонизации в нём нет. В явном тестовом режиме (`CQA_MODE=test`, `CQA_EVALUATOR=test`)
функции, которых ещё нет у A, заменяются заглушками из `testmode.py`: `score` без
арифметики и с `total_score=null`, hash с отдельным префиксом, заведомо не канонический.
Как только функция A реализована, она получает приоритет. В production заглушки
недостижимы, а отсутствие функции даёт явный 503 `configuration_error`.

`business_ready` равно `true`, только если работает настоящий домен и есть
настроенный профиль.

## Схема миграций и восстановления

| Ревизия | Содержание |
|---|---|
| `0001` | Разговоры и ревизии, приватные исходные записи, чек-листы, профили, корпуса, пакеты, задания, попытки, вызовы, оценки, триггер неизменности автоматического результата |
| `0002` | Приватная диагностика попыток. Перестройка `evaluations`: у задания может быть несколько failed-результатов и не больше одного нормального |
| `0003` | Апелляции с частичным уникальным индексом «одна открытая на критерий», решения только на добавление |

Миграции выполняются при старте и работают от пустой БД и от предыдущей версии с
сохранением данных. Понижение версии намеренно не поддерживается.

Долговечность: WAL, `synchronous=FULL`, `foreign_keys=ON`, busy timeout 5000 мс, запись
через `BEGIN IMMEDIATE`, параметры SQL скрыты из сообщений об ошибках. Сеть и вызовы
оценщика выполняются вне транзакций.

Восстановление выполняется при каждой выдаче задания, в том числе первой после старта:

1. Задание `running` с истёкшим lease получает попытку `expired`. Незавершённые вызовы
   становятся `unknown`: не ноль и не удаляются.
2. Если остались попытки и бюджет, задание переходит в `retry_wait`, иначе в `failed`.
3. Завершённые задания оценщик повторно не вызывают.
4. Опоздавший ответ старой попытки получает `LeaseLost`. Известный расход при этом
   сохраняется в её записи, результат новой попытки не заменяется.

поэтому сейчас он выгружается как `other`. Нужно решение, добавлять ли его.

**R-8. Предпосылки оценщика A для тестового профиля.** `Evaluator` A принимает только
свои `prompt_version` и `preprocessing_version`, а встроенный тестовый профиль сервера
предназначен для синтетического оценщика foundation. Это ожидаемо, но при подключении
настоящего оценщика профиль должен содержать версии A.

## Принятые решения в пределах контракта

Проверьте, подходят ли они C и интеграции.

- Версии чек-листа выдаются от новых к старым, очередь апелляций — от старых к новым.
- Неизвестный критерий в апелляции даёт 422, апелляция на failed-оценку — 409.
- Ручной retry разрешён из `failed` и `retry_wait` и при необходимости увеличивает
  `max_attempts`, но не выше 10. Исчерпанный бюджет или прошедший deadline дают 409.
- Failed-артефакт сохраняется как оценка только при окончательном отказе и без вызова
  `score`. Невалидный артефакт хранится приватно как диагностика попытки.
- Стоимость в экспорте считается только по вызовам самого задания. У переиспользованного
  результата это `0` и `cost_complete=true`; стоимость исходной оценки ему не приписывается.
- Reuse с артефактом, который не прошёл `validate_artifact` для новой версии, не падает,
  а выполняет свежую оценку.
- Доступность аудио (`available`/`unknown`) обновляется в документе ревизии по факту
  обращения; на content hash это не влияет. Истёкшая ссылка оставляет `unknown`.
- Состояние `cancelled` не используется: операции отмены в контракте нет. Штатная
  остановка переводит задание в `retry_wait`, а если попытки или бюджет исчерпаны, в `failed`.
  В поиске по флагу такое состояние всё равно даёт `failed` и `unknown`; тест задаёт его
  прямой записью в БД.

## Известные ограничения

- Частые перезапуски расходуют попытки: это следствие требования считать каждую начатую
  попытку. После трёх остановок подряд задание придётся повторить вручную.
- Задание может завершиться позже `deadline_at`, но не больше чем на запас, если оценщик
  реагирует на отмену. Оценщик, игнорирующий отмену, удержит слот исполнителя: `wait_for`
  ждёт завершения отмены, и такой случай отдельно не обрабатывается.
- Если при зависшем необязательном reviewer оценщик не вернётся в пределах запаса, initial
  будет потерян. С A на заглушке транспорта возврат происходит сразу после deadline.
- Реальные провайдеры, ключи и API организаторов не проверялись, стоимость и точность
  не измерены.
- Формат записей организаторов не подтверждён (R-2). Production-профиля нет (R-1).
- Аудио проверено только на заглушках. `content_hash` и `mapping` не заполняются, поэтому
  `alignment_status` остаётся `unverified` и точный seek недоступен.
- Адрес хоста аудио проверяется до запроса, но соединение к нему не привязано: остаётся
  узкое окно для DNS rebinding. Основная защита — allowlist и запрет перенаправлений
  за его пределы.
- Ограничение размера аудио без объявленной длины срабатывает обрывом потока, потому
  что заголовки к этому моменту уже отправлены.
- На одну БД нужен один исполнитель: внутри API или отдельным процессом
  `cqa_api.worker`. Отдельный процесс проверен разовым smoke, автотеста на него нет.
- Поиск поддерживает один выбранный флаг: «любой флаг» и несколько ID контрактом не
  предусмотрены. Настоящий `Evaluator` A через поиск по флагу не прогонялся, флаги получены
  настоящим `cqa_domain` из запланированных тестом ответов. Точность обнаружения флагов
  моделью не измерялась.
- Локально проверено только на Windows, Node 22.20.0. Linux проверяется в CI.
- Браузерные E2E с настоящим API локально не выполнялись: нет Chromium. Экран поиска — зона C.
