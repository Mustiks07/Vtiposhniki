# Claude C: веб-интерфейс и полная браузерная приёмка CQA

Версия: 1.0, 7 ноября 2026 года. Читать после `00_MASTER_SPEC.md` целиком.
Роль: один из трёх Claude-агентов; владелец всего интерфейса и браузерных E2E. Плановая нагрузка — 100 единиц.
Ветка: `claude/web-e2e`, созданная от проверенного foundation SHA, который передаёт GPT Pro.
Этот документ описывает будущую реализацию; его наличие не означает готовый код, ветку или пройденные проверки.

## 1. Результат работы

Проверяющий открывает новый разговор, понимает, почему выставлена оценка, находит спорное место и принимает мотивированное решение с корректным пересчётом.
Пользователь также импортирует данные, запускает пакет, создаёт новую версию чек-листа и применяет неизвестный ранее критерий без изменения кода.
Основные действия доступны без регистрации. Интерфейс русский; оригинальные RU/KZ/EN сообщения сохраняют исходный текст.
Учебные слайды задают рабочий процесс, но не требуют копии макета, круговой диаграммы или двух аудиодорожек.
Поставить работающий React/TypeScript/Vite frontend, браузерные тесты и собственный handoff для интегратора.

## 2. Исключительная область и границы

- Владеешь `apps/web/**`: экраны, компоненты, стили, клиент API, локальные UI-тесты, браузерные E2E и их конфигурация.
- Дополнительно разрешён только собственный отчёт `docs/handoffs/claude-web-e2e.md`; общие документы меняет GPT Pro.
- Общие manifests, lockfiles, CI, корневой README, `packages/cqa_contracts`, `contracts` и `fixtures/contracts` принадлежат GPT Pro.
- Зависимости и изменения общих команд сначала предложи GPT Pro с причиной; согласованный lockfile не обновляй параллельно.
- Claude A владеет рубрикой, оценщиком и арифметикой; Claude B — HTTP API, БД, заданиями, версиями, апелляциями и экспортом.
- Не создавай второй backend, локальный движок баллов, собственную схему ответов или незаметную браузерную базу результатов.
- Не редактируй чужие модули для обхода проблемы; передай владельцу минимальный воспроизводимый пример и ожидаемый контракт.
- Не добавляй авторизацию, управление организациями, CRM-интеграцию, сложные дашборды или другие enterprise-функции.
- Отделённый API и обычная веб-сборка учитывают будущую адаптацию к Dynamics 365; саму интеграцию не реализуем.

## 3. Условия старта и независимая разработка

Сначала получи от GPT Pro foundation SHA, утверждённые команды запуска, TypeScript-контракты и синтетические контрактные примеры.
Убедись, что foundation собирается; работай в собственном clone/worktree и с отдельной runtime-БД тестового backend.
Полной готовности backend ждать не нужно: разрабатывай компоненты и состояния на согласованных contract fixtures.
Fixture-режим должен быть явно тестовым и изолированным; он не поставляет результаты в демонстрационный режим.
Сразу согласуй с B первый работающий маршрут импорта, чтение разговора, запуск задания и получение результата.
Как только доступен этот вертикальный срез, переключи сквозной сценарий на настоящий API и интегрируй его до остальных экранов.
Все финальные E2E работают через настоящий backend; перехваты HTTP с подстановкой успешных ответов не заменяют приёмку.
Если контракт не покрывает состояние, оформи запрос GPT Pro: поле/операция, пользовательская причина, пример и совместимость.
Generated TypeScript не править руками; обновление получать от согласованного SHA вместе с остальными агентами.

## 5. Навигация и общие правила UX

Основные разделы: «Диалоги», «Чек-листы», «Апелляции»; карточка разговора объединяет оригинал и выбранную оценку.
Сохраняй в URL идентификатор карточки/пакета и необходимые фильтры, чтобы обновление страницы восстанавливало контекст.
После refresh получай состояние с сервера. В localStorage не хранить разговоры, оценки, подписанные URL или ключи.
Отменяй устаревшие запросы при смене карточки; ответ предыдущего разговора не должен появляться в новом.
Показывай понятный следующий шаг в empty/error/partial состояниях; отсутствие данных не изображай нулевой оценкой.
Кнопки записи защищены от повторного отправления; для создания пакета используй согласованную идемпотентность API.
Технические correlation_id доступны при ошибке для диагностики; секретные настройки и сырые ошибки провайдера в UI не выводятся.
Длинные тексты, казахские символы и английские реплики не обрезать без возможности раскрытия; горизонтальная прокрутка контролируема.
Оригинальные сообщения показывать как текст, без исполнения HTML/Markdown из транскрипта; ссылки обрабатывать безопасно.

## 6. Диалоги, импорт и пакетная оценка

Импорт поддерживает organizer API с редактируемым `group_id` и загрузку JSON в согласованном формате.
UI не принимает произвольный адрес для серверного скачивания: секретный адрес организаторов находится на backend.
Проверяй читаемость JSON и обязательные поля формы, а содержательную проверку импорта оставляй серверу; показывай его ошибки точно.
Импорт v1 атомарный: при ошибке любой записи весь запрос отклонён. Показывай индекс и безопасную причину из errors; не изображай частичное сохранение.
В списке доступны фильтры языка/канала/статуса, пагинация, выбор одного или нескольких разговоров и переход к карточке.
Не зашивай DEV, 65 записей, 10 контрольных примеров, известные ID или конкретные темы как ограничения приложения.
Один external_id может иметь несколько revisions; показывай выбранную revision и не объединяй разные тексты молча.
Перед запуском пользователь видит выбранную версию чек-листа, доступный профиль оценщика и режим fresh/reuse_if_compatible.
Fresh означает новый вызов оценщика; reuse отображается только при подтверждённом сервером происхождении результата.
Пакет закрепляет версии при создании; последующее редактирование чек-листа не меняет уже запущенный пакет.
Экран пакета показывает итоговые счётчики и состояние каждого задания, сохраняя успешно обработанные элементы при частичном сбое.
Отображай `queued`, `running`, `retry_wait`, `succeeded`, `failed`; `cancelled` — только если отмена поддержана контрактом.
Для retry_wait показывай попытку/предел и следующую попытку, если доступны; не обещай точное время завершения без данных.
Job succeeded и evaluation partial — разные состояния: «Обработка завершена, оценка неполная» с объяснением отсутствующего итога.
Повтор разрешён только в допустимом API-состоянии; временный сетевой обрыв чтения не должен автоматически создавать новый пакет.
При refresh/reconnect восстанавливай чтение существующего пакета; polling ограничен, прекращается после финального состояния.

## 7. Редактор чек-листов и неизменяемые версии

Чек-лист редактируется как новый draft; сохранение создаёт новую версию, а не меняет правила уже существующих оценок.
Поля критерия: название, определение, тип binary/scale/flag, вес, варианты ответа, смысл ступеней, условия N/A и секция.
Дополнительные согласованные поля: инструкции для канала, требования к доказательствам, необходимость источника и значения, включающие флаг.
Позволяй добавлять, удалять, заменять и переставлять критерии; стабильные ID существующих критериев сохраняются при редактировании.
Для нового критерия используй непрозрачный ID согласно контракту; логика UI не должна зависеть от номеров исходной восьмёрки.
У каждого варианта показывай `raw_value`, словесный anchor и явную `score_fraction`; decimal передаётся строкой по контракту.
Для шкалы с нулевой нижней ступенью можно предложить raw/max, но пользователь видит и подтверждает отображение вариантов в доли.
Ненулевая нижняя ступень и обратная шкала требуют явного подтверждения mapping; не выбирай трактовку молча.
Проверяй диапазон доли 0–1, неотрицательный вес и обязательные подписи; окончательную валидацию выполняет API.
Для flag вес равен нулю, score_fraction отсутствует; отдельно задаётся, какой ответ означает обнаружение нарушения.
Разрешение N/A требует текстового условия; N/A не является вариантом с нулевой долей и не служит обозначением неизвестного ответа.
Поддержи секции и критерии без секции. Сохранение не навязывает исходные восемь названий, шкалы или суммарный вес 100.
До сохранения покажи ошибки рядом с полями; после серверного отказа сохрани введённый draft и отобрази общую причину.
Список версий показывает даты/идентификаторы; сравнение раскрывает изменения определений, вариантов, N/A, весов и секций.
Запуск с новой версией доступен из редактора/списка; старые карточки продолжают использовать свои исходные версии.
При изменении только веса UI сообщает о подтверждённом переиспользовании raw-оценки и показывает источник пересчёта, если сервер его применил.

## 8. Карточка оценки, доказательства и аудио

На широком экране транскрипт и критерии видны рядом; на узком остаются понятные переключение и возврат к выбранному фрагменту.
У сообщения видны роль, текст и `timestamp_original`; для MM:SS не придумывать календарную дату, ISO-источник также доступен дословно.
Предполагаемые этапы и предупреждения ASR показывать как аннотации; не удалять bot/system, дубли или хвост после события завершения.
По критерию показать выбранный ответ, шкалу, вес, взвешенный результат, обоснование, доказательства, ограничения и причины проверки.
Исходная ступень `7/10` по №6 отображается отдельно от `10,5/15` до перераспределения N/A; это одна оценка, не две ступени шкалы.
Для нормализованного вклада в общий итог использовать отдельную подпись и данные сервера; не смешивать его с исходным весом.
Frontend форматирует числа из ScoreSummary, но не реализует вторую формулу, округление или пересчёт после апелляции.
Покажи итог до двух знаков; `no_applicable_weight` и `incomplete_evaluation` имеют разные объяснения и не отображаются как 0/100.
Секции показывают полученный/применимый вес и процент секции; проценты секций не складываются в общий итог.
Грубые нарушения отображаются отдельным флагом и объяснением; не обнуляй итог и не считай «Да» успехом для flag.
N/A сопровождается причиной неприменимости; undetermined — отдельным ограничением, partial — состоянием результата.
Различай полноту automatic и effective. Если человек мотивированно закрыл все undetermined, показывай полный effective_score с явным человеческим происхождением, сохраняя partial и отсутствующий total у automatic. Confirmed без замены неопределённого ответа не делает оценку полной.
Клик по message/range evidence прокручивает и подсвечивает все указанные сообщения; границы диапазона включительные.
Цитата берётся из исходных сообщений по ID; для пропуска действия показывается проверенный участок, а не вымышленная цитата отсутствия.
Source evidence открывает безопасные метаданные и доступный фрагмент источника; отсутствующий источник обозначается, не подменяется догадкой.
Используй source_fragments из EvaluationView и source_chunk_id доказательства; отдельный неподтверждённый маршрут получения текста источника не вводи.
При конфликте reviewer выводи конкретную причину проверки; не заменяй automatic_final и не показывай confidence как вероятность правильности.
Карточка различает automatic и effective, версию разговора/чек-листа/профиля и происхождение reused результата без перегрузки основного экрана.
В деталях запуска покажи полученные от API названия фактически вызванных моделей, длительность и полную стоимость со всеми попытками/reviewer/fallback; неизвестная часть стоимости обозначается явно.
При наличии записи используй реальный аудиоплеер или описанный API fallback; loading, недоступность и ошибка воспроизведения видимы.
Переход к секунде разрешён только при подтверждённом mapping от сервера; при неизвестном mapping переходи к реплике и обозначай ограничение.
Не вычисляй позицию аудио вычитанием первого timestamp без подтверждения; не рисуй фиктивные дорожки оператора/клиента или волну записи.
Имя/данные, скрытые организаторами, остаются маркерами исходника; UI не раскрывает их и не трактует как автоматически пропущенное действие.

## 9. Апелляции, решения, сравнение и экспорт

Из выбранного критерия пользователь подаёт апелляцию с комментарием; после сохранения обращение доступно в общей очереди и карточке.
Проверяющий видит спорный критерий, исходный ответ AI, комментарий, текущие доказательства и исходный фрагмент разговора.
Действия «Подтвердить» и «Изменить» требуют причины; replacement при изменении соответствует типу ответа, шкале и правилам N/A.
Замена не может содержать произвольную числовую ступень; форма следует текущему снимку критерия, а не последней версии другого чек-листа.
После решения заново получи EvaluationView: сервер возвращает effective_score; automatic_score и исходные доказательства не перезаписываются.
Покажи сравнение «AI → решение → итог после пересмотра», включая причину, дату и изменившийся вклад критерия.
Конфликт revision/повторного решения требует обновления данных и явного повторного действия; не перезаписывай решение другого окна.
Передавай expected_revision. На пару evaluation_id + criterion_id допустима одна открытая апелляция; новая после решения ссылается на текущую revision. Confirmed сохраняет действующее значение, changed заменяет его, история остаётся доступной.
Повторная AI-оценка создаёт новую карточку; старые апелляции не переносятся на неё автоматически и не исчезают из истории.
Экспорт запускает серверные маршруты JSON/CSV с явным выбором automatic/effective; UI не пересобирает второй формат самостоятельно.
Экспорт пакета сохраняет partial/failed элементы; стоимость unknown/null отображается как неизвестная, а не нулевая.
Стандартный экспорт использует безопасный серверный DTO: решения, баллы, статусы, версии, message ID и reason codes без свободного текста и транскриптов. Полные обоснования доступны в карточке. Расширенный текстовый экспорт показывать только при отдельно реализованном и согласованном режиме обезличивания.

## 10. Доступность и состояния ошибок

Все формы имеют видимые labels, подсказки формата и связанные сообщения ошибок; цвет не является единственным обозначением статуса.
Все действия, диалоги, выбор критериев и переходы к доказательствам доступны с клавиатуры; фокус заметен и возвращается после закрытия окна.
Асинхронные статусы доступны через подходящие live regions без постоянного озвучивания каждого polling-ответа.
Модальные окна имеют корректное управление фокусом; подтверждение решения не теряется при ошибке сети.
Предусмотри пустой список, отсутствующую оценку, удалённый/неизвестный ID, невалидный импорт, конфликт версии и недоступный сервер.
Сетевая ошибка чтения предлагает повторить чтение; ошибка записи сохраняет ввод и учитывает идемпотентность, не обещая, что запись не произошла.
Проверь desktop и узкий экран, увеличение масштаба 200%, длинные обоснования и RU/KZ/EN без наложения элементов.

## 11. Браузерная приёмка на настоящем API

Используй согласованный foundation-инструмент E2E (предпочтительно Playwright) внутри apps/web; установка зависимостей — через GPT Pro.
Детерминированные сценарии могут использовать явно тестовый evaluator на реальном backend; mock HTTP не считается их прохождением.
Для ошибочных/partial сценариев согласуй с B безопасный тестовый setup, недоступный в обычном режиме; не придумывай новые публичные маршруты.
Финальный smoke с реальным провайдером выполняется отдельно с доступным ключом; отсутствие ключа отмечается как непроведённая проверка.
Не проверяй точный AI-балл случайного живого ответа; проверяй происхождение, допустимость, доказательства и полный пользовательский процесс.

| ID | Сценарий | Условие приёмки |
|---|---|---|
| E01 | Новый ID/текст через JSON и organizer import | Разговор доступен через настоящий API, количество записей не зашито |
| E02 | RU/KZ/EN и voice_call | Оригинальные тексты/роли/время сохранены и читаемы |

## 12. Этапы передачи и готовность

Первый handoff: каркас и вертикальный срез импорт → пакет → карточка на API; приложи контрактные пробелы до расширения UI.
Второй: редактор/версии, доказательства/аудио и апелляции; передай работающий цикл изменения критерия и пересмотра оценки.
Третий: вся матрица E01–E20, доступность, refresh/recovery и сравнение версий; ошибки backend направляй B с воспроизведением.
Финальный: чистая сборка, typecheck, UI-тесты и E2E; согласованный real-provider smoke и пятиминутный сценарий защиты.
Демо: 1 минута диалог; 2 минуты оценка/доказательства/N/A; 1 минута апелляция/решение; 1 минута изменение критерия и применение.
Handoff содержит ветку/SHA, выполненные R/E ID, команды и фактические результаты, используемые режимы оценщика, артефакты сбоев и ограничения.
Не записывай «готово», если финальный UI работает только с fixtures, проверка skipped или основной процесс требует ручной правки БД.
В Git не включать реальные транскрипты/аудио, runtime-БД, секреты, подписанные URL, приватные screenshots/traces; тестовые артефакты очищать от них.
