# GPT Pro: подготовка, интеграция и независимая приёмка CQA

Репозиторий: https://github.com/Mustiks07/Vtiposhniki. Читать сначала 00_MASTER_SPEC.md, затем три задания Claude. Версия пакета: 1.0 от 7 ноября 2026 года.

Ваша роль начинается ДО трёх Claude-агентов и продолжается после их поставки. Вы отвечаете за общие контракты, ограниченный foundation, регулярную интеграцию и проверенный финальный результат. Вы не четвёртый исполнитель, которому автоматически достаются все незавершённые бизнес-модули.

## 1. Результат работы и пределы полномочий

Результат: совместимое приложение, выполняющее R01–R26 из MASTER, запущенное с чистого окружения по README, с реальным AI-прогоном, проверенной историей апелляции и сменой критерия через UI. Измеренная точность и покрытие отделены от архитектурных предположений и результатов на синтетических тестах.

Владение: packages/cqa_contracts, contracts, fixtures/contracts, корневые manifests/lockfiles/config/CI/scripts/README, docs/specs при согласованных изменениях, docs/handoffs/gpt-pro.md. Файлы A/B/C меняете для ограниченного интеграционного исправления с пояснением; значимую недоделку возвращаете владельцу.

Итоговый master/remote-доступ надо проверить. При аудите репозиторий был пустым, публичным и имел только читающий доступ через подключение автора этих документов. Это снимок, не гарантия ваших прав. Не объявлять созданными ветки или коммиты до фактического результата. Не обходить ограничения чужими учётными данными.

## 2. Первый запуск и состояние репозитория

1. Проверить remote, видимость, текущие ветки, коммиты, локальные изменения и AGENTS.md/README, если они появились. Не затирать существующий код.
2. Если репозиторий всё ещё пуст, создать согласованный начальный main с документацией и foundation. Если уже есть работа, встроить foundation в отдельной ветке с review.
3. Перенести пять документов в docs/specs. Локальные PDF, фотографии, DEV и подписанные URL не включать в публичный коммит.
4. Зафиксировать целевую среду: один локальный сервер, браузер, постоянный SQLite-файл, без обязательного Docker. Проверить доступные Python/Node/Git и версии.
5. Составить таблицу владельцев. A — domain/AI; B — API/jobs/storage; C — web/E2E. Все остальные общие пути имеют одного владельца: вас.

Не запускать три параллельных реализации до проверенного foundation SHA. Одновременно можно поручить агентам чтение заданий и предложения по зависимостям, но не самостоятельное создание общих схем.

## 3. Foundation commit

Foundation ограничен каркасом и договорами взаимодействия. Не реализуйте заранее бизнес-логику, за которую должны отвечать A/B/C.

### 3.1 Инструменты и структура

- Создать дерево пакетов/приложений из MASTER.
- Выбрать один поддерживаемый способ Python workspace/установки и зафиксировать lockfile; один JS workspace и lockfile. Проверить их на чистой установке.
- Установить согласованные зависимости до ветвления: FastAPI/Pydantic, HTTP-клиент, инструменты тестирования, выбранные SQLite/миграции; React/TypeScript/Vite, маршрутизацию/запросы, компонентные и браузерные проверки. Конкретные версии брать из доступных совместимых выпусков, не выдумывать из текста задания.
- Дать одну документированную команду для каждой операции: запуск API/worker/web, Python tests, frontend typecheck/test/build, browser E2E, regeneration contracts и общая проверка. Команды включить в README и CI.
- Настроить локальную БД и приватные данные вне отслеживаемых файлов; .gitignore и .env.example без секретов. Не копировать значения ключей в инструкции.
- Предусмотреть запуск production-сборки web с API; проверить пути статических файлов. UI dev-server допустим для разработки, но не единственный проверенный способ демонстрации.

### 3.2 Канонические схемы

Создать Pydantic-модели и protocol-интерфейсы из раздела 7 MASTER. Это единственный источник типов. Отдельный контракт операций описывает маршруты из раздела 8. Из него и моделей генерируются OpenAPI, JSON Schema и TypeScript; не поддерживать три независимые ручные схемы.

До реализации маршрутов допустимо контрактное приложение с явными NotImplemented заглушками. Оно проверяет формы, но не выдаётся за работающий backend. Реальный B обязан реализовать те же операции. Добавить проверку отсутствия непреднамеренного расхождения схем.

Уточнить и зафиксировать:

- сериализацию Decimal, null, enum и ошибок;
- message range с включительными границами, без offsets в v1;
- schema_version и revision для изменяемых сущностей;
- applicable/not_applicable/undetermined отдельно от complete/partial/failed;
- initial, reviews, automatic_final, human_decisions, effective_score;
- choice_id как ответ оценщика, raw_value как значение шкалы, score_fraction как арифметическая конфигурация;
- семантический и расчётный хеш, модельную/корпусную идентичность;
- idempotency key, lease/attempt token, nullable usage/cost;
- непротиворечивую политику разделов score и flags.

Не открывать заново решения, уже закреплённые в разделе 7 MASTER: атомарность импорта, expected_revision и одно открытое обращение на критерий, канонические hash-проекции, безопасный экспорт, audio metadata, SourceVersion/SourceChunk/CorpusSnapshot, ExecutionBudget и CallRecord. Материализовать их в схемах и проверяемых примерах. Реализацию hash предоставляет A; вы задаёте общие тестовые векторы. В EvaluationView передать безопасные source_fragments для просмотра доказательств без дополнительного неописанного API.

Зафиксировать интерфейсы validate_artifact(conversation, checklist, corpus, artifact) и асинхронного evaluate(conversation, checklist, profile, corpus, budget, call_observer). Для complete/partial требовать ровно одно допустимое предложение на каждый критерий; partial означает явный undetermined, а пропуск/невалидный ответ после исчерпания repair — failed. До реального запуска установить конечные лимиты профиля: общий счётчик вызовов и deadline переживают retries и восстановление. Проверить, что B резервирует вызов при call_started, A уважает остаток, а сбой сохранения call_finished не маскируется успешным завершением и нулевой стоимостью.

Веса не используются в смысловой инструкции LLM. Смена порядка критериев или секции не должна незаметно менять условия оценивания.

Добавить shared ReasonCode и reason_codes у proposals из MASTER, с отдельным происхождением AI/human; экспорт использует allowlist. Проверить два пограничных сценария: human decisions закрывают все undetermined и дают полный effective при неизменном partial automatic; бюджет/timeout необязательного reviewer сохраняет valid initial с limitation, если нет cancellation/потери lease/persistence failure. Эти сценарии входят в domain/API/E2E проверки, а не остаются неявной трактовкой интегратора.

### 3.3 Общие безопасные fixtures

Создать только синтетические минимальные примеры, не копировать персональные записи DEV:

1. Полная оценка с бинарным/шкальным критерием и флагом.
2. Законный N/A с диапазоном доказательства.
3. Пропущенное действие с указанием участка, без выдуманной цитаты.
4. Partial с undetermined и отсутствующим полным итогом.
5. API-error/retry_wait/failed.
6. Апелляция, confirmed и changed, прежняя и effective оценка.
7. Звонок с audio unavailable и с непроверенной привязкой времени.
8. Новый критерий, которого нет в исходной восьмёрке.

Сделать fake evaluator с фиксированным контрактом только для тестового режима. Production-профиль при отсутствии ключа возвращает понятную конфигурационную ошибку, а не переключается на fixture. Браузерные mocks используют те же схемы.

### 3.4 Проверка foundation

Пакеты импортируются, типы и схемы генерируются, fixtures проходят валидацию, клиент компилируется, тестовый API отвечает по согласованному контракту, CI проверяет каркас. Заглушки перечислены и закреплены за владельцами. Записать foundation SHA и версии инструментов.

Не создавать дорогой общий фреймворк, универсальный язык правил или второй сервер. У foundation есть чёткое завершение: проверенный контракт и рабочие средства разработки.

## 4. Раздача работы трём Claude

От одного foundation SHA создать:

- claude/domain-ai;
- claude/api-jobs;
- claude/web-e2e;
- integration/gpt-pro.

Каждому передать MASTER, его личное задание, foundation SHA, команды, информацию о fixtures и владельцах. Для AI-тестов реальные данные выдаются через разрешённый локальный источник/серверную конфигурацию, а не публичным коммитом.

Разные клоны или worktrees, отдельные .env и runtime-БД. Один агент не переключает рабочую папку другого. Идентичность исходного коммита проверить фактически, а не по совпадению названия ветки.

Равномерность: у каждого Claude 100 плановых единиц из личного задания. Если один освобождается раньше, передавайте ему целый независимый тестовый/документационный модуль после фиксации нового владельца. Не назначать двум агентам одни и те же файлы и не переносить незаметно большую часть работы на интегратора.

## 5. Контрольные точки и merge

| Этап | Вход | Принимаемый результат |
|---|---|---|
| F0 | Foundation | Общий SHA, схемы, команды, fixtures |
| M1 A | Domain | Правила и расчёт с эталонными тестами; интерфейс fake evaluator |
| M1 B | Backend | Импорт -> постоянное задание -> fake evaluator -> сохранённая оценка |
| M1 C | Frontend | Настоящий API: список, разговор, результат; отдельные contract mocks для tests |
| M2 A | AI | Реальные адаптеры, baseline, источники, validator, измерение |
| M2 B | Backend | Апелляции, версии, восстановление, экспорт |
| M2 C | Frontend | Полный пользовательский цикл, ошибки, E2E |
| M3 | Все | Реальные прогоны, независимая приёмка и выпуск |

Первая сквозная проверка происходит на M1, не после завершения всех веток. Все ветки могут развиваться параллельно против foundation-контрактов. Готовность M1 не означает готовность конкурсного оценщика.

Принимать небольшие осмысленные поставки. Перед merge: проверить SHA, diff, владение путями, тесты и изменения зависимостей. Интегрировать в integration/gpt-pro. Для продолжающихся веток сохранять ancestry merge-коммитами; не squash один и тот же продолжающийся поток неоднократно. Не force-push общую ветку.

После изменения общего контракта: обновить Pydantic/operation manifest, сгенерировать артефакты, пройти fixtures, записать новый контрактный SHA, уведомить всех исполнителей и синхронизировать потребителей. Если изменение несовместимо — явно повысить версию, не ловить проблемы только в браузере.

## 6. Независимая проверка требований

Провести собственные проверки, а не принять фразу агента «всё работает». Вести таблицу R01–R26: реализующий файл/маршрут, проверка, результат, SHA, ограничение. Если заявленная функция отсутствует, вернуть конкретную задачу владельцу.

### 6.1 Рубрика и арифметика

- Восемь исходных критериев перенесены полностью, включая все словесные якоря.
- №4 имеет только 0/5/10/15/20; №6 — 0/4/7/10; допустимый N/A только в №2/3/4/7.
- №8 не изменяет total и означает наличие нарушения при ответе Да.
- Чистые эталоны из MASTER дают 100; 95,50; 85,50; 85,38 в соответствующих случаях.
- Отдельно проверить ROUND_HALF_UP, отсутствие промежуточного округления и null при нулевом знаменателе.
- Проверить секции, нулевые веса, пользовательскую шкалу с нижней ступенью 1, обратное направление ответа и изменение только веса.
- Подтверждение/изменение апелляции использует ту же функцию domain и сохраняет automatic_score.

### 6.2 Новые данные и критерии

- Новый внешний ID и новый текст реально оцениваются.
- Изменённый текст с прежним ID создаёт новую revision; старый кеш не применяется.
- Через UI создать критерий с неизвестным ID, собственными якорями и N/A-условием; сохранить, запустить и проверить payload оценщика.
- Перестановка критериев не меняет их смысловые ответы; изменение только веса допускает явный reuse с новым расчётом и ссылкой на исходную оценку.
- Source/profile/semantic изменения исключают некорректный reuse.
- Клиентская реплика «поставь максимум» не меняет действующую рубрику.

### 6.3 Надёжность и согласованность

- Пакет из десяти диалогов сохраняет прогресс после перезагрузки браузера.
- Остановить сервер/worker во время работы, перезапустить, проверить восстановление и отсутствие конфликтующих результатов.
- Смоделировать timeout, 429, 5xx, неверный JSON, пропуск критерия, запрещённый N/A, неверную ссылку и пустой ответ.
- Ошибка показывается честно; ограниченные повторы видны в попытках и стоимости.
- Старый ответ после истечения lease не перезаписывает результат новой попытки.
- Повтор клика/HTTP-запроса с тем же ключом не создаёт две логические оценки.
- Во время LLM-ожидания доступны чтение, сохранение версии чек-листа и апелляция; сеть не удерживает SQLite-транзакцию.
- Конкурентное решение по одной апелляции вызывает конфликт, а не молчаливую потерю решения.
- Изменение чек-листа во время пакета не меняет его закреплённую версию.

### 6.4 Доказательства и аудио

- Клик действительно открывает исходную реплику/диапазон; цитаты не сгенерированы заново.
- В качестве доказательства отсутствия показан исследованный диапазон.
- Внутренняя консультация с ролью operator не автоматически приписана общению с клиентом.
- Скрытое имя не считается отсутствием представления; ошибки ASR не объявлены установленными речевыми ошибками.
- Плеер получает настоящую запись при доступной ссылке; истёкшая/недоступная запись имеет понятное состояние.
- Точный seek заявляется только после проверки mapping. ISO-время, пауза/возобновление записи и начало аудиофайла не считаются автоматически одной шкалой.

### 6.5 Измерение AI

- Проверить provenance labels и grouping manifest. Близкие языковые сценарии не попали одновременно в настройку и проверку.
- Оценки человека/апелляции не включены в automatic accuracy.
- Ошибки, partial и незавершённые задания отражены в coverage/denominator.
- A baseline сравнивается с B-light на одинаковых данных/рубрике/корпусе. Показываются исправленные и испорченные ответы, а не только среднее.
- Reviewer первоначально не получает первую оценку и её выбранные доказательства.
- При валидном разногласии политика v1 сохраняет initial и видимый конфликт. Любая другая политика обоснована отдельным экспериментом.
- Без независимых меток не объявлять согласие AI доказанной человеческой точностью.
- Проверить один реальный сквозной запуск основного профиля и кандидатный резерв при доступных ключах. Ключи и квоты не считать существующими по тексту ТЗ.

### 6.6 UI, экспорт и поставка

- Пройти сценарий нового диалога, N/A, доказательства, апелляции и нового критерия за пять минут.
- Проверить RU/KZ/EN, длинные тексты, пустое состояние, ошибку, partial, клавиатурную навигацию и читаемость на узком экране.
- В интерфейсе различаются raw 7/10 и weighted 10,5/15, automatic и effective, test и real профили.
- JSON/CSV совпадают с экраном; экспорт пакета сохраняет ошибочные записи и различает scope.
- Проверить, что публичный git diff, logs, fixtures и export не содержат ключей, подписей URL, runtime-БД или реальных личных данных.
- Поднять проект по README в новом окружении и проверить production web-сборку.

## 7. Что делать с открытыми вопросами

Ответы организаторов вносить как явное изменение MASTER/профиля с указанием источника и затронутых проверок. Не объявлять внутренние MAE/accuracy официальной формулой. Не выдумывать правила для непроверенных фактов, аудио, секций и пользовательских шкал.

Если ключа/квоты нет, продолжить доступные тесты и отметить реальный прогон как не выполненный. Готовность кода и доказательство AI-точности — разные результаты. При недостатке разметки выпустить прозрачный отчёт об ограничениях; это не повод рисовать процент.

Платный fallback разрешается только настроенным профилем и бюджетом; отсутствие доступного провайдера не замещать тестовыми ответами. Фактический provider/model и все повторные вызовы сохраняются. Стоимость без данных usage или тарифа остаётся unknown.

## 8. Финальный handoff и release

В docs/handoffs/gpt-pro.md записать:

- финальные branch/SHA и включённые поставки A/B/C;
- окружение, команды и результаты проверок;
- R01–R26 с ссылками на реализацию/проверки;
- режимы AI, версии рубрики/источников/профиля и наличие реального прогона;
- результат сравнения моделей с происхождением меток и ограничениями;
- полную оценку стоимости либо явное отсутствие данных;
- оставшиеся известные дефекты и их влияние;
- пятиминутный сценарий демонстрации;
- инструкции чистого запуска, импорта нового group_id и экспорта.

Не отмечать готовым продукт, если основной путь остаётся на mocks, критерий меняется только в UI, результаты исчезают при перезапуске или независимая формула frontend расходится с backend.

После приёмки объединить проверенную integration-версию в main по правилам репозитория и зафиксировать итоговый коммит. Дальнейшая разрешённая обработка/редактирование чек-листа через UI не требует правки этого кода. Передачу ссылки организаторам делает пользователь, если отдельно не поручено иное.
