Версия пакета: 1.0, 7 ноября 2026 года. Репозиторий: https://github.com/Mustiks07/Vtiposhniki.

Прочитай полностью `00_MASTER_SPEC.md`. Этот документ конкретизирует твою работу и не меняет общий контракт. Ты реализуешь серверную часть на отдельной ветке; Claude A отвечает за предметную логику и AI, Claude C — за интерфейс, GPT Pro — за foundation, общие схемы и интеграцию.

Твой результат — работающий API с постоянными данными, восстановлением заданий, версиями оценок, апелляциями и безопасным экспортом. HTTP-ответ о запуске не означает завершённую оценку: состояние должно переживать перезапуск приложения.

Не реализуй собственную формулу баллов, промпты, retrieval, reviewer или клиентский интерфейс. Вызывай `validate_checklist`, `validate_artifact`, `score` и `evaluate` из согласованных пакетов A. При апелляции используй тот же `score`, что и при первоначальной оценке.

## 3. Контракты и конфигурация

Единственный источник публичных типов — Pydantic-модели foundation. Реальные маршруты, `operation_id`, HTTP-коды и сериализация обязаны совпадать с его operation contract. Generated OpenAPI/TypeScript не редактируй руками.

Все публичные объекты сохраняют `schema_version`. Серверное время — UTC ISO 8601. Идентификаторы непрозрачны; внешние ID не определяют первичные ключи или ожидаемые оценки.

Единая ошибка: `code`, `message`, `details`, `retryable`, `correlation_id`. Возвращай безопасное сообщение, а не необработанный ответ внешнего сервиса. Конфликт версии не маскируй успешным перезаписыванием.

Интеграционные вызовы: `validate_artifact(conversation, checklist, corpus, artifact)` и асинхронный `evaluate(conversation, checklist, profile, corpus, budget, call_observer)`. Передавай закреплённый corpus и общий ExecutionBudget; validator проверяет также source_chunk_id и сохранённые фрагменты. Evaluate возвращает EvaluationArtifact без итогового балла.

`CQA_DATASET_URL`, `GEMINI_API_KEY`, `DEEPSEEK_API_KEY`, `OPENROUTER_API_KEY` читаются сервером из окружения/приватной настройки. Ключи не передаются из браузера, не сохраняются в профиле модели, ответах API, БД попыток или логах.

Профиль содержит безопасные настройки и ссылку на серверную конфигурацию. Отсутствующий ключ или недоступный провайдер дают явное диагностируемое состояние. Переключение провайдера допустимо только по закреплённому профилю с сохранением фактических метаданных.

## 4. Импорт без потери исходных данных

Поддержи `organizer_api` с `group_id` и JSON-payload установленного формата. Сервер сам использует секретный адрес организаторов; браузер не задаёт произвольный URL скачивания.

1. Проверь transport status, размер, JSON, `isSuccess`, контейнер `data.records` и каждый разговор.
2. Только после проверки всего payload сохрани исходные записи приватно и нормализованное представление одной короткой транзакцией.
3. Преобразуй `agent chat`/`voice call` в контрактные каналы; роли сохраняй без догадок.
4. Присвой сообщениям ID `m0001`, `m0002` и далее внутри revision, `ordinal` и `source_index`; глобальная ссылка включает revision разговора.
5. Сохрани `text` и `timestamp_original` дословно; `parsed_time` добавляй только при успешном разборе.
6. MM:SS не превращай в выдуманную календарную дату. Ошибку разбора времени показывай предупреждением.
7. Новое содержание при прежнем external_id создаёт новую revision/content_hash; старая revision остаётся доступной оценкам.
8. Повторный импорт идентичной записи не создаёт бесконечные дубли; результат сообщает о найденном совпадении.

Не удаляй повторяющиеся реплики, ASR-шум, внутренние консультации или поздние слова после события завершения. Не сортируй исходник так, чтобы потерять исходную последовательность. Нормализованные аннотации не заменяют оригинал.

Не фиксируй количество 65, конкретные DEV-ID, темы или только RU-звонки в production-логике. Не выполняй автоматическую оценку или сетевой вызов AI как скрытый побочный эффект импорта.

Импорт v1 атомарный: при любой невалидной записи не сохраняется ни одна запись запроса. Верни безопасный список errors с индексами и причинами. Одинаковые повторы external_id внутри payload сворачиваются; конфликтующее содержание одного external_id в одном payload отклоняется как неоднозначное. Лимит размера задаётся конфигурацией; нарушение получает понятную ошибку. Формат ответа берётся из foundation.

## 5. SQLite, версии и постоянные данные

Режим поставки — один экземпляр приложения, постоянный локальный диск, SQLite WAL и один управляемый исполнитель. Ограниченная параллельность ожидающих AI-запросов не требует нескольких независимых scheduler-процессов.

- Настрой внешние ключи, согласованный busy timeout и короткие транзакции; режим долговечности зафиксируй в конфигурации и handoff.
- Не размещай WAL-БД на сетевом диске и не копируй только основной файл как «готовый backup» во время работы.
- Миграции должны работать на пустой БД и обновлять предыдущую поддерживаемую схему без удаления пользовательских данных.
- Храни связи между revisions разговоров, checklist versions, профилями, corpus snapshots, заданиями, попытками, результатами и решениями.
- Публичный ключ или версия объекта не должны ссылаться на изменяемый снимок правил.
- Не держи DB-транзакцию открытой во время вызова модели, скачивания данных или ожидания аудио.

До постановки пакета закрепи конкретные версии разговора, чек-листа, профиля и corpus snapshot. `profile_id` разрешается в версию до выполнения. Редактирование любого из этих объектов не меняет уже запущенный пакет.

Сохраняй `EvaluationArtifact`, результат `score`, использованные chunks и метаданные вызовов. EvaluationView содержит `source_fragments[]`: текст фактически использованных фрагментов и безопасные реквизиты их закреплённых SourceVersion. Локальная карточка получает доказательства даже после обновления источника. Исходный AI-артефакт неизменяем; новая оценка создаёт новый результат.

## 6. Устойчивая очередь и наблюдаемость

Состояния: `queued -> running -> succeeded / retry_wait / failed`; `cancelled` только при реализованной и согласованной отмене. Храни задания в БД, а не только в памяти или framework background task.

При получении задания атомарно проверь допустимое состояние, создай attempt ID и lease. Транзакцию закрой до `evaluate`. При необходимости продлевай lease короткой записью только для текущего владельца.

Каждая попытка содержит время начала/окончания, timeout, состояние, безопасную причину ошибки и известный расход. Реализуй awaitable `call_observer` событий `call_started`/`call_finished` с call_id и родительским attempt_id. Сохраняй CallRecord идемпотентно, включая purpose primary/review/repair/fallback, запрошенную/фактическую модель, finish_reason, nullable usage/cost и price_version; AI-пакет в БД не пишет.

В `call_started` атомарно проверь действующий attempt/lease, deadline и оставшийся ExecutionBudget, зарезервируй один внешний вызов и запиши событие. Повтор одного события не расходует бюджет второй раз; каждый новый внешний запрос имеет новый call_id. A ждёт успешного callback перед отправкой: при ошибке persistence или BudgetExceeded запрос не отправляется.

В `call_finished` сохрани известный исход и расход; ошибка записи не скрывается и не позволяет объявить попытку успешно зафиксированной. Если внешний запрос завершился, а его расход неизвестен, сохраняй unknown/null, не ноль. Позднее событие учитывается только в своей попытке и не заменяет результат новой. Отмена/timeout не удаляют известные события; секретов и chain-of-thought в callback нет.

ExecutionBudget принадлежит logical_job_id и включает общий max_provider_calls/consumed_calls, закреплённый при первом запуске deadline_at и доступные лимиты токенов/стоимости. Все попытки B и вложенные primary/review/repair/fallback A используют один остаток. Восстановление, ручной retry и смена попытки не сбрасывают бюджет или deadline. Исчерпанное задание не повторяется автоматически; численные лимиты конечны и проверены до живого запуска.

На завершении проверь актуальность attempt ID/lease. В одной транзакции сохрани артефакт, проверенный расчёт, привязку результата и состояние задания. Опоздавший ответ старой попытки не может заменить результат новой.

Повторы ограничены одновременно числом попыток, общим ExecutionBudget/deadline и настройками профиля. Временные сетевые ошибки/лимиты и окончательные ошибки различаются. Не повторяй бесконечно неверный ключ, запрещённую конфигурацию или невалидный вход; произведение вложенных retry-лимитов не обходит общий предел.

При запуске приложения восстанови ожидающие работы, `retry_wait` и истёкшие lease по согласованной политике. Уже завершённые задания не вызывают AI повторно. Не обещай строго однократный внешний вызов: после аварии повтор возможен, но логический результат не дублируется.

Идемпотентность создания пакета: один ключ с тем же нормализованным запросом возвращает тот же пакет; тот же ключ с другим запросом даёт конфликт. Сохранение ключа и создание пакета/заданий выполняются атомарно.

`POST /jobs/{id}/retry` работает только в разрешённых состояниях и не создаёт гонку с действующей попыткой. Новая попытка сохраняет историю. Повтор завершённой оценки оформляется новым запуском, а не стиранием результата.

Различай состояние задания и качество результата: complete/partial содержат ровно один structurally valid proposal на каждый запрошенный критерий. Complete не содержит undetermined; partial содержит хотя бы один, допустимы все undetermined. Partial может завершить job как succeeded, но полного балла нет. Undetermined не превращается в N/A.
Отсутствие полного балла здесь относится к automatic. После human decisions передавай объединённые proposals в score: все undetermined закрыты — effective может быть полным; original artifact остаётся partial и automatic total=null. Confirmed сохраняет текущее значение и сам по себе не закрывает undetermined. Метрики AI не включают человеческое заполнение.

Необязательный reviewer после valid initial может пропускаться/завершаться без вывода из-за бюджета, timeout или отказа. Сохрани исходную оценку с limitation, если lease действителен и обязательные события сохранены. Закрытие готового результата после лимита дополнительных вызовов не является новым AI-запросом. Без initial бюджетный отказ — failed; cancellation, потерю lease и persistence failure по-прежнему не маскировать.

Пропущенный/повторный критерий, запрещённый choice, невалидная структура или ссылка не превращаются в partial/undetermined автоматически. A выполняет ограниченный repair в общем бюджете; после исчерпания — failed. B повторно вызывает validate_artifact с corpus перед принятием результата. Частично извлечённые сведения невалидного ответа остаются диагностикой, не полноценной оценкой.

Не смешивай progress с придуманным процентом готовности модели. UI получает наблюдаемые состояния/счётчики. Неизвестные токены/стоимость — null/unknown, не ноль. Известные расходы не теряются при неудачной попытке.

## 7. Переиспользование и пересчёт

Единственную канонизацию/hash реализует A в cqa_domain; GPT Pro закрепляет входные схемы и тестовые векторы. Вызывай её для SHA-256 от UTF-8 canonical JSON, не пиши второй алгоритм. Текст/исходное время не переписываются, порядок сообщений сохраняется. Content hash учитывает канал, язык, текст/роли/время и известную дату, но не external_id или signed audio URL.

Semantic checklist канонизируется по стабильным ID критериев/choices без весов, score_fraction, секций и порядка отображения; определения, названия/labels/anchors, raw_value, тип, условия N/A, channel_instructions, evidence_policy, requires_reference и flag_when_choice_ids входят. Изменение любого из этих смысловых полей исключает reuse прежнего вердикта. Scoring hash учитывает веса, score_fraction, секции и округление. В `reuse_if_compatible` при неизменной семантике и совместимом входе переиспользуй допустимые автоматические предложения, создай новый результат, вызови `score` с новой расчётной конфигурацией и сохрани provenance.

Новый текст, роли, время, определения, шкалы/якоря, условия N/A, источники или профиль исключают устаревшее переиспользование. Evaluation reuse key включает content hash, semantic checklist, profile/settings/prompt/preprocessing версии и corpus snapshot; если звук использован — его content hash. Проверяй revision/hash, не только external_id. Ручные решения не являются сырьём для автоматического кеша; alias модели не доказывает неизменность её весов.

Режим `fresh` действительно вызывает оценщик, даже если совместимый результат существует. Старые апелляции не переносятся на новый результат. Затраты повторного расчёта не выдавай за стоимость первоначальных AI-вызовов.

## 8. Апелляции и конкурентные решения

Создавай обращение по существующей оценке и существующему критерию её зафиксированного чек-листа. Комментарий обязателен по контракту; неизвестные ID и неподдерживаемые изменения отклоняются.

Решение — `confirmed` либо `changed`; причина обязательна. При `changed` проверь replacement proposal по исходной версии критерия: допустимый ответ/N/A, существование доказательств и согласованность данных.

Решение принимает `expected_revision`. В одной транзакции проверь revision/состояние, запиши решение, сформируй эффективные предложения и сохрани пересчёт через `cqa_domain.score`. Устаревшая revision получает HTTP 409. Проверка и запись не разделяются сетевым вызовом.

Не изменяй `initial`, `reviews` или `automatic_final`. Карточка и экспорт различают automatic/effective. Подтверждение не теряет историю, а изменение не выдаётся за новую оценку модели.

Для пары evaluation_id + criterion_id допускается одно открытое обращение, в том числе при конкурентных запросах. После решения разрешено новое обращение с явной ссылкой на текущую revision effective результата. Confirmed оставляет действующее значение, changed заменяет его; effective учитывает последние принятые решения по критериям, история только дополняется.

## 10. Аудио, экспорт и секреты

Аудиомаршрут принимает внутренний conversation ID, не произвольный URL. Исходный audio_url остаётся приватным; signed query-параметры не попадают в логи, JSON-карточку или экспорт.

Audio metadata содержит available/unavailable/unknown, внутренний access_path, content_hash nullable, alignment_status verified/unverified/unavailable и mapping nullable. Mapping создаётся после проверки. Истёкшая ссылка не доказывает отсутствия аудио. Без подтверждённого доступа к новому источнику сохраняется текстовый режим с ограничением.

Для серверной загрузки используй согласованные разрешённые хосты/схемы, проверку перенаправлений и ограничения времени/размера. Не допускай доступа к локальным файлам, loopback/private/link-local адресам через URL импортированного разговора. Не создавай открытый proxy.

Поддержи согласованный режим выдачи аудио и Range, если он нужен выбранному плееру. Не буферизуй бесконтрольно весь файл. При недоступной записи верни понятное состояние; fallback не должен раскрывать секретную ссылку. Точный seek возможен только при подтверждённой временной привязке.

Экспорт v1 строится отдельным DTO по allowlist: ID, решения, баллы, статусы, версии и ссылки на сообщения по ID. Причины — только безопасные reason codes. По умолчанию нет транскрипта, свободного текста, source_fragments, signed URL, ключей или сырых персональных данных. Не сериализуй DB-модель/EvaluationView напрямую. Расширенный текстовый экспорт — отдельный явно обозначенный режим только после согласованной проверки обезличивания; полные доказательства доступны в локальной карточке.
CriterionProposal.reason_codes валидируется по shared ReasonCode из MASTER. A создаёт AI-коды; B формирует human_confirmed/human_changed для решений и replacement proposal, сохраняя свободную причину отдельно. Не выводи codes извлечением произвольного текста из rationale. При confirmed текущее proposal сохраняется, код подтверждения относится к Decision; при changed replacement имеет human_changed.

JSON и CSV сохраняют scope, версии, статусы и ограничения; незавершённые записи не исчезают. Обеспечь UTF-8, корректные кавычки/переносы и защиту CSV-ячеек от исполнения формул. Не представляй наш формат как официальный формат сдачи организаторам.

## 11. Проверки, которые ты поставляешь

Запускай тесты на изолированных временных БД/каталогах. Чужие runtime-данные не очищай. Для сетевых сценариев используй управляемые HTTP-заглушки; платные вызовы не являются частью обычного тестового запуска.

1. Атомарный импорт: неизвестный ID, совпадение, новая revision, ошибка одной записи без сохранения остальных, одинаковые/конфликтующие повторы external_id внутри payload.
2. RU/KZ/EN, оба канала, MM:SS/ISO, неизвестная дата, повторяющиеся реплики и порядок source_index сохраняются.
3. Создание/изменение чек-листа вызывает валидацию A; изменение во время пакета не меняет pinned version.
4. Ключ идемпотентности: повтор запроса, другой payload с тем же ключом и конкурентные запросы.
5. Временная ошибка, retry_wait, лимит попыток, окончательная ошибка, timeout и невалидный артефакт.
6. Перезапуск с queued/running/retry_wait; истёкший lease; старый ответ после начала новой попытки.
7. Атомарность завершения: сбой между получением ответа и commit не оставляет succeeded без результата.
8. Полное coverage для complete/partial; undetermined не N/A; missing/invalid после repair дают failed; расходы неудачных/повторных вызовов сохранены.
9. Совместимый пересчёт вызывает score без AI; fresh вызывает AI; смена semantics/corpus/profile исключает reuse; внешнее имя/signed URL не подменяют content hash.
10. Одно открытое обращение на критерий, последующее обращение после решения, expected_revision/409, confirmed текущего effective, changed и неизменность automatic_final.
11. Во время медленного AI-вызова доступны чтение и сохранение обращения; нет удержания DB-транзакции.
12. Runtime OpenAPI совпадает с foundation; export automatic/effective содержит partial/failed и reason codes, но не свободный текст/секреты; локальный EvaluationView содержит pinned source_fragments.
13. Аудио: недоступность, запрещённый адрес/redirect, пределы загрузки, отсутствие signed URL в ответах и логах.
14. Пустая БД, миграция поддерживаемой версии и запуск без ключей с явным отказом реальной оценки.
15. Идемпотентные started/finished, уникальные call_id, отказ persistence на started запрещает сеть, отказ на finished запрещает успешный commit; неизвестная стоимость не ноль.
16. Общий бюджет и deadline ограничивают все вложенные вызовы и попытки; restart/manual retry не сбрасывают остаток; конкурентные резервации не превышают max_provider_calls.

Арифметические эталоны принадлежат тестам A. Здесь проверяй правильный вызов domain и сохранение результата, не копируя формулу в серверный тестовый «оракул».

## 12. Этапы интеграции и handoff

- B1: миграции, импорт, список/карточка, минимальный вертикальный проход через foundation test evaluator до постоянного job/result. Передай C работающий API рано.
- B2: устойчивая очередь, повтор/восстановление, версии, реальный адаптер A через тот же интерфейс, учёт вызовов.
- B3: апелляции, совместимый пересчёт, безопасный экспорт/аудио, конкурентные проверки и полный handoff.

Тестовый оценщик foundation разрешён только явным тестовым режимом. Не добавляй скрытый fallback на fixtures при ошибке ключа/API. Отдельный интеграционный прогон с реальным провайдером выполняется после получения локальной конфигурации; результат и ограничения фиксируются честно.

Передай GPT Pro ветку/SHA, выполненные пункты, команды и фактические результаты тестов, схему миграций/восстановления, настройки без значений, известные ограничения и предложения по общему контракту. Не объявляй общий проект принятым по результатам одних серверных тестов.
