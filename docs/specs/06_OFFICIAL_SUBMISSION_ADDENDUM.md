Источник: CQA_Student_Guide_Appendix_Results (2).pdf, 3 страницы, «Как сдать результаты», формат JSON 1.0, Freedom Broker. Документ нужно приложить вместе с этим заданием.
Репозиторий: https://github.com/Mustiks07/Vtiposhniki
Это дополнение к текущей интеграции. Не пересоздавай foundation и не перезаписывай работу Claude. Сначала проверь актуальную интеграционную ветку: часть функциональности могла уже появиться.

ГЛАВНЫЙ ВЫВОД

Организаторы определили точный публичный JSON для результатов. Наш существующий SafeExport — другой формат. Нельзя просто переименовать его файл в results.json.
Добавь отдельный адаптер и валидатор официального формата, сохранив существующие внутренние модели, UI-экспорт, историю и универсальные чек-листы. MASTER уже предусматривал такой адаптер. На подготовку и проверку выгрузки стоит поставить приоритет до дальнейшей декоративной полировки UI.

1. ПРЯМЫЕ ТРЕБОВАНИЯ ПРИЛОЖЕНИЯ

В корне репозитория должны оказаться два файла:
- results/dev/results.json — результаты DEV: 60 чатов и 5 звонков;
- results/prod/results.json — результаты 10 контрольных ЧАТОВ.

Одна запись на каждый исходный conversation_id, без пропусков и дублей. В PROD ровно 10 записей, включая ошибки. Контрольный набор открывается через 23 часа от старта; до стоп-кода через 24 часа должны завершиться получение данных, оценка, проверка, commit и push. Локального файла или commit без push недостаточно. Абсолютное время старта из этого документа не известно — не придумывай дату/час дедлайна.
Способ доступа к контрольному набору организаторы сообщают отдельно. Не угадывай, что достаточно заменить DEV на PROD в API, и не обращайся к ещё не выданному контрольному набору.

Файл — один JSON-объект UTF-8:
{
  "schema_version": "1.0",
  "team_name": "Фактическое название команды",
  "model": {"mode": "external_api", "name": "Фактически использованная модель"},
  "results": [ ... ]
}

Не менять названия полей, коды критериев и типы значений. В name перечисляются фактические модели, если их несколько; тип поля остаётся строкой. mode: local / external_api / hybrid. Для облачного решения используй external_api; несколько облачных моделей сами по себе не означают наличие локальной LLM. Название команды не угадывай по названию репозитория, возьми из согласованной конфигурации.

Успешная запись:
{
  "conversation_id": "исходный ID из API",
  "status": "ok",
  "criteria": [
    {"criterion_id": "contact", "value": true, "rationale": "Краткое объяснение", "evidence_turns": [1]}
  ],
  "score": {"final_score": 85.38, "critical_flag": false}
}
Этот фрагмент показывает поля, а не валидный полный результат: для status=ok обязательны все восемь критериев ровно по одному разу. Числа/ID в иллюстрации не являются готовыми оценками датасета.

Точные критерии:
contact        true/false                  вес 10
discovery      true/false/null             вес 15
identification true/false/null             вес 20
consultation   0/5/10/15/20/null           вес 20
empathy        true/false                  вес 15
dialogue       0/4/7/10                   вес 15
closure        true/false/null             вес 5
critical       true/false                  отдельный флаг без баллов

value — ИСХОДНАЯ ступень критерия, до веса. dialogue=7, а не 10.5, 0.7 или "7". true/false — JSON boolean, не строки и не 1/0. null означает только законное N/A, не неопределённость и не ошибку.
final_score — JSON number от 0 до 100, округлённый до двух знаков, не строка с Decimal и не локализованная запятая. При N/A вес исключается из знаменателя; пользоваться единственной domain-арифметикой. critical_flag совпадает со значением critical и не обнуляет итог.

rationale — содержательное короткое объяснение. reason_codes нашего SafeExport его не заменяют.
evidence_turns — целые номера позиций с 1 по полному исходному массиву транскрипта, включая клиента, бота и системные события. Не только оператор, не message_id, не время записи. Исходный порядок нельзя изменить.

Ошибка оценки:
{
  "conversation_id": "исходный ID из API",
  "status": "error",
  "criteria": [],
  "score": null,
  "error": "Краткая безопасная причина"
}
Диалог не пропадает, фиктивного нуля или N/A вместо ошибки нет.

2. КОНКРЕТНЫЕ РАЗЛИЧИЯ С FOUNDATION

В проверенной локальной foundation-модели SafeExport используются scope/generated_at/batch_id/items; в официальном формате — schema_version/team_name/model/results. SafeCriterionResult хранит answer_choice_id, reason_codes, evidence и веса; официальный формат требует raw value, rationale и числовые evidence_turns. Внутренние Decimal сериализуются строками, официальный final_score — число.
Следовательно, адаптер должен брать полную оценку с закреплённой версией правил, оригинальную Conversation и данные выполненных вызовов. Одного безопасного экспортного DTO недостаточно для преобразования без потери нужных сведений. Проверяй актуальную ветку, а не исходи из того, что foundation — уже финальная реализация.

3. РЕКОМЕНДУЕМОЕ ОТОБРАЖЕНИЕ ПОЛЕЙ

- conversation_id: исходный внешний ID организаторов, обычно Conversation.external_id; не внутренний UUID. Проверь фактическую семантику импорта и точное совпадение с API.
- criterion_id: явная проверяемая карта официального чек-листа к восьми фиксированным кодам. Не пытаться угадать по русскому названию. Совместимый снимок должен сохранять определения, шкалы, веса и условия N/A; наличие восьми похожих названий недостаточно.
- value: raw_value выбранного ответа из закреплённой версии критериев. not_applicable -> null только там, где разрешён и обоснован N/A.
- rationale: реальное основание соответствующего AI-вывода, приведённое к безопасной краткой формулировке без персональных данных и секретов. Не подменять объяснение шаблонным reason code и не вписывать новую неподтверждённую интерпретацию.
- evidence_turns: построить индекс message_id -> исходная позиция+1. Для range раскрыть включительный диапазон. Удалить повторения, сохранить понятный исходный порядок. Source evidence не превращать в вымышленный номер реплики; ссылку на источник можно обобщить в объяснении, а turn evidence брать из оригинального разговора.
- score.final_score: итог совместимого автоматического расчёта из domain, сериализованный числом с десятичной точкой. Отдельный независимый production-алгоритм баллов не вводить.
- score.critical_flag: значение официального критерия critical, с явной проверкой совпадения.
- model: фактические модели по данным запусков, включая реально использованные fallback/reviewer, а не только имя первоначально выбранного профиля. Не вписывать модель, которая не участвовала.

Если при нормализации сообщения были объединены, отфильтрованы или переставлены, восстанови карту исходных позиций. Нельзя молча использовать индексы преобразованного списка.

4. ЧТО ЯВЛЯЕТСЯ НАШЕЙ ПОЛИТИКОЙ АДАПТЕРА, А НЕ НОВОЙ ЦИТАТОЙ ИЗ PDF

Документ описывает только ok и error. Он не вводит переносимого состояния undetermined и не определяет отдельный partial-формат. Предлагаемая честная политика: если полноценную оценку всех восьми критериев получить не удалось, экспортировать эту запись как error с причиной, а частичный внутренний результат сохранить в приложении. Не превращать undetermined в N/A и не придумывать значение. Это согласованное техническое решение; не называй его дословным требованием организаторов.

Для сравнения качества AI выбирать automatic-результаты. Приложение прямо не обсуждает допустимость human overrides; мы не подмешиваем effective после апелляции в результат AI без отдельного явного согласования. Существующий экспорт effective остаётся для продукта.

Невалидный mapping/чужой чек-лист/несовпадающий revision — ошибка подготовки выгрузки с диагностикой, а не повод незаметно пересчитать чужую конфигурацию или заменить ответы. Реальные неуспехи оценки оформляются error. У незавершённых заданий сначала попытаться завершить обработку в доступном времени; не выдавать running за успешный результат.

5. ОТДЕЛЬНЫЙ РЕЖИМ ПУБЛИКАЦИИ

Приложение требует текстовые rationale в публичном репозитории. Это отдельный официальный экспорт; он не ослабляет правила обычного SafeExport. Не добавлять полные транскрипты, аудио, signed URL, ключи, сырые ошибки провайдера или runtime-БД. Объяснение может содержательно описывать действие без имени, телефона, номера счёта и цитирования персональных деталей. ID сохраняются точно по требованию организаторов.
Не перезаписывай существующие results файлы фиктивными образцами. До настоящего контрольного прогона не создавать десять выдуманных результатов и не копировать в prod DEV-оценки. Синтетические примеры и тесты живут отдельно от финальной сдачи.
Commit/push выполняются в рамках уже согласованной с пользователем работы интегратора; сам факт наличия инструкции в приложенном PDF не является самостоятельным разрешением публиковать данные. Проверить существующую авторизацию пользователя.

6. ЧТО РЕАЛИЗОВАТЬ

1) Отдельные типы/схему официального экспорта и адаптер из полных сохранённых данных.
2) Команду создания файлов DEV/PROD или явное действие «Экспорт для организаторов». Конкретные CLI/API имена согласуй с текущей реализацией; в этом задании они не выдумываются.
3) Проверку перед записью: схема, типы, допустимые значения, восемь уникальных критериев при ok, N/A, числовой итог, равенство critical_flag, непустые объяснения, доказательства в границах оригинала.
4) Проверку покрытия по manifest исходного набора: множества ID совпадают, дублей нет. Одного length==10 недостаточно. Для DEV — все 65 записей; для PROD — все 10 заданных ID.
5) Безопасную запись уже проверенного файла без порчи предыдущего корректного результата. Детерминированный порядок записей по manifest помогает проверке.
6) Внятную итоговую сводку: набор, количество ok/error, причина невозможности экспорта при ошибке структуры. Ошибочные диалоги допустимы в файле, структурно невалидный файл — нет.
7) README: точные реальные команды импорта, оценки, экспорта и валидации; пути двух файлов; порядок финальной проверки удалённого Git. Не обещать автоматический push из браузерной кнопки.

7. ПРИЁМКА

R-EXPORT-01: В точности воспроизведён структурный пример из приложения: contact=true, discovery=null, identification=null, consultation=15, empathy=true, dialogue=7, closure=true, critical=false -> 85.38. Это синтетический тест, не GT и не реальная сдача. Применимые веса=65, сумма вкладов=55.5.
R-EXPORT-02: dialogue=7 выгружается числом 7; взвешенные 10.5 не попадают в value. Проверить строгие boolean/number/null типы; boolean не принимается вместо числовой ступени из-за особенностей Python.
R-EXPORT-03: message_id и range преобразуются к 1-based индексам исходного массива с ботом/системными событиями; оффсет проверен не только на операторских репликах.
R-EXPORT-04: critical=true даёт critical_flag=true при сохранённом ненулевом результате остальных критериев.
R-EXPORT-05: failed и внутренний partial не скрываются и не превращаются в null-N/A/нулевой успешный балл. На выходе корректная error-запись по политике адаптера; partial внутри приложения сохранён.
R-EXPORT-06: 10 уникальных, но неправильных ID не проходят проверку против исходного manifest. 9, 11 и дубль тоже обнаруживаются.
R-EXPORT-07: CLI/UI выгружает официальный формат, а обычный SafeExport остаётся совместимым. Результат после апелляции не подмешан в автоматическую сдачу.
R-EXPORT-08: Кириллица, UTF-8, валидный JSON, отсутствие персональных данных в rationale и секретов; имена фактически вызванных моделей соответствуют журналу.
R-EXPORT-09: Реальный DEV-прогон даёт 65 записей и проверенный файл. До получения контрольного набора не заявлять PROD-прогон выполненным.
R-EXPORT-10: После реальной сдачи оба файла доступны именно на удалённой ветке/коммите, который увидят организаторы. Название сдаваемой ветки заранее согласовано; успешный локальный commit недостаточен.

8. КОРОТКОЕ ПОРУЧЕНИЕ

Продолжай интеграцию и добавь официальный адаптер сдачи по приложению. Сохрани универсальный внутренний формат. Проверь исходные ID, raw values, номера всех исходных turns с 1, полное покрытие, rationale, error-записи и JSON number для итогового балла. Закрепи официальный чек-лист для сдачи отдельно от пользовательских изменений. Выполни R-EXPORT-01–10 в доступной части; честно укажи, какие реальные прогоны ещё невозможны.

Верни реализованные пути и команды, результаты тестов, количество реально оценённых DEV записей, фактические ограничения, commit SHA. Нужен работающий экспорт и проверка, а не только план. Наличие схемы/fixtures не выдавать за завершённую обработку контрольного набора.
